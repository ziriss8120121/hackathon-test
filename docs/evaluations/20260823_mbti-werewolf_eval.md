## 概要

心理機能（MBTIの4機能スタック：Ne/Ti/Fe/Si等）を割り当てた4体のAIエージェントに、簡略版の人狼（特殊役職なし、夜フェーズなし、昼の議論3ターン＋1回の投票で終了）をプレイさせ、行動ルールの差が発言・疑われ方・勝敗に現れるかをログとして観察するシミュレーター。`PublicView`による役職情報の非対称性の構造的担保、seed駆動の役職割当・発言順、`Brain`インターフェースによる推論手段（stub/Ollama/Gemini）の差し替え、`run_log.json`を正本とした派生出力（summary/timeline/metrics.csv/result.html）、複数試合をseriesとして連続実行し機能別に集計する仕組みまでが、一貫した設計思想のもとに実装されている。

一方で本プロジェクトの上位文書が示す目的は、創発現象の研究ではなく「本番ハッカソンのテーマ選定に使える、実際に動かした制約・実現可能性・判断材料を得ること」（`docs/requirements.md` 3章）であり、MBTI人狼はそのための使い捨ての題材と明言されている。本評価軸はマルチエージェント・シミュレーションとしての創発性を測るものであるため、**プロジェクトの目的と評価軸の狙いが元々ずれている**点は前提として押さえておく必要がある。低いスコアの一部は「失敗」ではなく、この目的の不一致に由来する。

## 評価詳細

### A. 創発設計 — 4/10

#### 評価

**世界ルール側（≒5）**: ゲーム進行の実装精度は高い。役職構成の妥当性検証、`PublicView`による役職情報の非対称性の構造的強制（人狼だけが仲間IDを受け取り、村人視点では`teammates`が必ず空になる）、同数得票時の決定的タイブレーク、投票候補からの自己除外は、いずれもコードレベルで一貫して守られ、テストでも保証されている。ただし「世界」としては非常に薄い。空間も資源も状態遷移もなく、世界の実体は共有された発言ログのみである。3ターン議論して1回投票し、1人処刑した時点で即終了するため、多段的なダイナミクスが生まれる余地が構造的にほとんどない。リファレンス実装の座標系・場所容量・距離依存の火災知覚・通信トポロジ制約と比べると、世界モデルの機構的な厚みが1段階以上少ない。

**行動自由度側（≒3.5）**: エージェントが受け取る状況データ自体はクリーンである。`alive_ids`・`vote_candidates`・未加工の発言ログのみで、「誰が怪しい」といった評価済み情報は一切含まれない。誰が人狼かの推理と投票先の判断は完全にLLMに委ねられており、この部分は本物の自由度がある。

問題は人格側にある。`FUNCTION_RULES`は数値の生データではなく、話し方そのものを指示する文章である（「断定を避け、思いつく可能性を複数並べて話す」「矛盾を見つけたら誰のどの発言かを指して具体的に指摘する」）。それがシステムプロンプトに直接埋め込まれ、「行動ルールに沿った話し方をしてください」と遵守を明示的に求められる。投票プロンプトの「自分の立場にとって有利になる相手に投票してください」は、リファレンス実装が意図的に避けた「最適化タスクの明示」に相当する（ただし勝利条件の提示に近く、「逃げろ」ほど直接的な行動指示ではない）。

さらに本質的な問題として、**観察したい従属変数が、プロンプトに注入した独立変数と同一である**という循環がある。`metrics.py`は`hypothesis_count`・`agreement_count`・`rebuttal_count`を数えるが、`functions.py`はNeに「仮説を2つ以上挙げろ」、Feに「同意を示せ」、Tiに「矛盾を指摘しろ」と指示している。しかも各機能の`note`欄が測定結果を先回りして予言している（「仮説数に差が出やすい」「同調が多く、Tiと対比が付く」）。つまり測定されるのは創発ではなく指示への追従率である。プロジェクト自身も`functions.py`のdocstringで「行動指示として扱う」と明言しており、この設計は意図的なものだが、創発性を問う本評価軸とは方向が異なる。

harmonic balanceの観点では、世界ルールの薄さと行動自由度の低さが両方効くため、「5-6: ルールは明確だが行動誘導あり」の帯の下限を割る。

- `src/mbti_werewolf/agents/functions.py:3-4` — docstring「エージェントの振る舞いを分けるための**行動指示**として扱う」（プロジェクト自身の位置づけ）

### B. 世界設定 — 5/10

#### 評価

人狼はLLMマルチエージェント研究で最も採用例の多い題材の一つであり、シナリオそのものの独創性は高くない。MBTI×人狼という掛け合わせにはわずかな新規性があるが、MBTI自体は構成概念妥当性が弱いポップ心理学であり、プロジェクト側も`README.md:10-11`で「実在人物の診断や評価ではない。フィクション設定として扱っている」と明示的に切り離している。

実世界接続については、人狼というゲーム自体は欺瞞検知・集団説得・少数派影響といった社会科学的に意味のある構造を潜在的に持つが、本プロジェクトはその方向に踏み込んでいない。上位文書の目的は一貫して「チームがAIエージェント開発を一周して制約を知ること」であり、実世界の組織・市場・意思決定ダイナミクスのモデル化は意図的にスコープ外に置かれている。

ただし、まったく問いが無いわけではない。`docs/requirements.md:155`には「今回見たいのは『どのMBTIタイプが本当に強いか』ではなく、行動ルールの違いがログや勝敗、疑われ方に現れるかである」という、反証可能な形の問いが明記されている。これは控えめではあるが「性格特性の付与がLLMエージェントの集団的帰結に影響するか」という、LLMエージェント研究として成立しうる問いではある。空虚な空間を動くだけのシミュレーションとは明確に異なる。

「妥当だが既視感のあるシナリオ」の帯に素直に当てはまる。

- `src/mbti_werewolf/README.md:10-11` — 「実在人物の診断や評価ではない…フィクション設定として扱っている」

### C. 発展性 — 7/10

#### コード拡張性（4.5/5）

本プロジェクトの最大の強みである。`README.md:142-143`が宣言する「依存は外から内へ一方向。`engine`と`agents`は脳の具体実装をimportしない」が実際に守られており、推論手段の追加は`brains/`とレジストリのみで完結する。心理機能の追加は`FUNCTION_RULES`への1エントリ、MBTIタイプは`TYPE_STACKS`に16タイプ全てが定義済み。4人/8人/16人版はCLIオプションで既にパラメータ化されている（`README.md:52`）。

特筆すべきは**実験基盤としての作り込み**である。プロンプトは版ディレクトリ（`prompts/v1/`）で管理され「文面を変えるときはv2を作って古い版を残す」という方針が明文化されている——これは実験の来歴管理であり、リファレンス実装には無かった観点である。設定は`config/default.json`に外部化され、`default.json → --config → CLI引数 → 画面フォーム`の優先順位で統合されたうえで、確定条件が試合ごとに`config.json`として保存される。`--games 100 --seed 42`で連続実行でき、`base_seed + run_index - 1`によりseries全体が再現可能。`series_summary.md`は心理機能別に勝率・平均発言数・平均疑われ数を集計し、`metrics.csv`は1行1プレイヤーで縦連結すればそのまま表計算で分析できる。さらに`roles.py`のdocstringが示すとおり、心理機能は固定順・役職はseed割当という設計により「同じ機能が村人のときと人狼のときの差」を比較でき、発言順をランダム化して発言量比較の偏りを除いている——これは条件比較のための統制設計そのものである。

つまり「仮説検証や条件比較を重ねられる研究プラットフォーム」という要件を、コード側は既に相当程度満たしている。

#### 将来展望（2.5/5）

プロジェクト直下の`README.md`には将来計画の節が無く、セットアップ・実行・出力の説明に終始する。上位文書に散在する形では、`docs/requirements.md` 7.3のWant要件（FR-11: 16人版のMBTI16タイプ拡張）、`config.py:29-30`の`history_mode`（過去ログ参照、F-18/F-39）、`design.md:474`の「Siは将来のhistory_mode検証で主役になる」といった技術的な拡張パスが記されており、方向性が皆無というわけではない。

しかし研究的深度は不足している。自分たちで立てた「行動ルールの差が結果に現れるか」という問いに対し、最も明白かつ価値のある次の実験——**行動ルールを与えない対照条件を置いたアブレーション**——の計画が無い。同様に、何試合で有意差を論じるのかという統計的設計、創発を定量化する指標の妥当性検証、複数LLMモデル間の比較設計（Geminiは「品質比較用」と一言あるのみ）のいずれも記述がない。上位`CLAUDE.md`の「Current Implementation Focus」に挙がる次の改善項目もresult.htmlの可読性・スマホ閲覧といったUI寄りのものが中心である。

### D. 技術実装 — 7/10

#### LLM利用（2.7/3）

洗練されている。特筆すべきは**形式の失敗と意味の失敗を層で分離した設計**で、`brains/base.py`のdocstringが明示するとおり、Brain層がJSON形式の検証・形式リトライ・通信リトライ・待機時間計測を担い、Agent層が意味の検証（投票先が生存者か）と再要求を担う。これによりログから「何が崩れた結果なのか」を後から判別できる。リファレンス実装にもなかった観点である。

`extract_json()`は素のパース→コードフェンス除去→最初の`{`から最後の`}`までの切り出しと3経路を試す。形式が崩れると温度を`0.8 → 0.5 → 0.2`と下げつつ形式指定を強めて再送する。通信失敗は`unreachable`/`rate_limited`/`timeout`/`invalid_response`に分類され、再試行可能な種別のみ指数バックオフで再送される。Ollamaはネイティブの`format: "json"`、Geminiは`responseMimeType: application/json`と、プロバイダごとに適切なパラメータを選択。Gemini無料枠に対しては呼び出し間隔を7秒強制し、429を`rate_limited`として記録する（自動フォールバックせず失敗として残す判断も、実験記録としては正しい）。

#### メモリ設計（1.0/3）— 明確な弱点

`src/`配下を`memory`および「記憶」で全文検索してもヒットが1件も無い。エージェントのメモリ機構は存在しない。各ターンでエージェントに渡される文脈は、これまでの全発言を生テキストのまま連結した`speech_log`のみであり、本評価軸が明確に否定する「単なるログダンプ」そのものである。自分の言葉で状況を要約して次ターンへ引き継ぐ自己生成メモリ（リファレンス実装のself-feedback機構）も、疑いの推移を保持する信念状態も、コンテキストの窓管理も無い。`referenced_history_ids`は常に空配列で埋められている。

3ターン×4人＝12発言という現在の規模では生ログ連結でも実用上は破綻しないが、自分たちが計画する8人・16人版ではそのまま破綻する。`Si`の行動ルールが「過去の発言を振り返る」であり、設計書が「Siは将来のhistory_mode検証で主役になる」と述べていることから、チームはメモリの重要性を認識しつつ未着手であると読める。

#### コード品質（1.9/2）

ハッカソン水準としては非常に高い。全モジュールの冒頭docstringが責務・対応する設計書の章番号・**なぜそう設計したかの理由**を記述している。dataclassと型ヒントが徹底され、命名も一貫。関心の分離（進行/プロンプト組み立て/推論/出力生成/画面）が明快。後方互換への配慮も意図的で、`roles.py:49-53`は確定していない値のキー自体を出力しないことで旧ログ形式を壊さないようにしている。

#### シミュレーション正確性（1.7/2）

進行は`_discuss()`・`_collect_votes()`のシーケンシャルなループで、並行実行由来の競合状態は原理的に発生しない。乱数は`_setup_rng = random.Random(config.seed)`と`_fallback_rng = random.Random(config.seed + 1)`のように系統を分離しており、フォールバック抽選が割当の再現性を乱さない設計になっている。Ollama呼び出しにも`config.seed + self._call_index`で呼び出しごとに決定的なseedを渡している。`test_reproducibility.py`が同一seedでの割当・発言順・投票先・勝敗の一致を検証する。減点要因は、LLM側の出力揺れにより完全な再現には至らないこと（コード・テストとも正直に認めている）と、リファレンス実装の4フェーズ同期実行に比べステップ機構自体が問う余地の少ない構造であることの2点にとどまる。

## 総評

### 優れている点

- 形式の失敗（Brain層）と意味の失敗（Agent層）を層で分離し、ログから「何が崩れたのか」を判別できるようにした設計は、リファレンス実装にも無い明確な長所である
- `PublicView`が役職情報の非対称性を構造レベルで担保し、`test_role_isolation.py`で漏洩がないことまで検証している
- プロンプトの版ディレクトリ管理、確定条件の試合ごとの保存、`base_seed`によるseries全体の再現性と、実験の来歴管理が一貫している
- `--games 100`の連続実行、`series_summary.md`の機能別集計、`metrics.csv`の縦連結分析まで、条件比較のための基盤が既に動く形で実装されている
- 心理機能は固定順・役職はseed割当・発言順はランダム化という統制設計により、交絡を意識した比較ができるようになっている
- 全モジュールのdocstringが「何をするか」に加えて「なぜそう設計したか」を記述しており、ハッカソン水準としては際立って可読性が高い

### 改善点・提言

1. **対照条件を置く（最優先）**: 行動ルールを与えないプレイヤーを混ぜた条件、または全員ルール無しの条件を作り、`metrics.py`の指標が有意に変わるかを見る。これが無いと、現在の測定は「指示への追従率」の測定にとどまり、自分たちで立てた問いに答えられない。
2. **性格特性を生データ化する**: 創発性を狙う方向へ寄せるなら、`FUNCTION_RULES`の散文的な話法指示をやめ、各機能の重みベクトル等の数値として渡し、それをどう発話に落とすかの判断をLLMに委ねる。
3. **投票プロンプトから目的の明示を外す**: `system_vote.md:27`の「有利になる相手に投票してください」を削り、勝利条件と役職の立場だけを提示して戦略選択自体をLLMに委ねる。
4. **自己生成メモリを導入する**: 発言ログの全文連結ではなく、各ターンでエージェント自身に「今の見立てと疑いの根拠」を短く自己記述させ、次ターンへ注入する。8人・16人版へ進む前提条件でもある。
5. **世界に厚みを持たせる**: 現状は1回の投票で即終了する。複数日の進行、夜フェーズ、占い師等の情報役職のいずれかを入れると、多段的な情報伝播と信念更新が起こり、創発を観察する余地が生まれる。
6. **READMEに研究計画を書く**: 検証したい仮説、対照条件の設計、必要試合数の見積もり、指標の妥当性をどう確認するかを明記する。コード側の実験基盤は既に強いので、記述を補うだけで発展性の評価は目に見えて上がる。

### 一言コメント

実験基盤としての作り込み——形式・意味の失敗の分離、プロンプトの版管理、seed統制、機能別集計——はハッカソン提出物として明確に上位の水準にある。一方で、観察したい行動差をプロンプトで直接指示しているため、測定しているものが創発ではなく指示への追従になっており、本評価軸の中核とは方向が異なる。対照条件の追加とメモリ設計の導入という2手で、既存の強い基盤をそのまま活かして評価を大きく引き上げられる。プロジェクト自身の目的（本番テーマ選定に向けた制約の把握）に照らせば十分に成功しており、この点数は目的の不一致を含んだ数字として読むべきである。

## 補足: リファレンス実装との比較

| 観点 | mbti-werewolf | リファレンス実装 |
|---|---|---|
| エージェント入力 | 生の発言ログ（クリーン）＋散文の行動ルール（誘導あり） | 数値のみ（occupancy, distance等） |
| 行動の自由度 | 推理・投票は自由、話法は指示 | 完全にLLM委任 |
| 世界の厚み | 発言ログのみ、1投票で終了 | 座標・容量・火災知覚・通信制約 |
| メモリ | 無し（生ログ連結） | LLM自己生成メモリのself-feedback |
| 再現性 | seed系統分離＋テストで保証 | ランダムシード未設定（指摘事項） |
| 実験の来歴管理 | プロンプト版管理・条件保存・series集計 | 無し |
| エラー処理 | 種別分類＋層分離＋バックオフ | try/except＋フォールバック |
| **合計** | **23.0** | **30.5** |

リファレンス実装が創発設計と世界設計で大きく上回る一方、再現性・実験来歴管理・エラー処理の分類ではmbti-werewolf側が上回っている。研究プラットフォームの「足回り」は既にできており、不足しているのは創発を起こす世界と入力の設計である。
