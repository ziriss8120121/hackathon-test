### 0.1 本書の位置づけ

| 文書 | 答えること | 例 |
| --- | --- | --- |
| 要求定義書 | なぜ作るか、何がほしいか | 本番テーマ選定に使える制約と判断材料がほしい |
| **要件定義書（本書）** | **システムは何を満たすべきか** | **1ゲームを人の介入なしで完走し、指定の項目を記録する** |
| 設計書 | どう実現するか | どのSDK・モデル・ライブラリ・ファイル構成を使うか |

### 0.2 上位文書との差異

本書では、操作画面から条件を設定して対戦を開始し、完了後に同じ画面で会話と結果を確認する流れを要件とした。上位文書の以下の記述は、この変更に合わせて更新が必要である。

| 上位文書の記述 | 本書での扱い |
| --- | --- |
| 制約・実行環境「リアルタイム対戦ではなく、自動バッチ実行」 | 実行の起動は画面のボタンから行う。会話を逐次表示しない点と、プレイヤーが全員AIである点は変わらない。 |
| 出力・画面要件「HTMLプロト画面は結果確認用でよい」 | 結果確認に加えて、条件設定と実行開始を担う。 |

### 0.3 本書で決めないこと（設計書に委ねる）

以下は本書では確定させない。要件を満たす範囲で設計書側で決定する。

- エージェントの脳として使う具体的なSDK、モデル、推論ランタイムの選定
- プロンプトの具体的な文面
- ファイルのschema詳細、ディレクトリ構成、ファイル分割方針
- 操作画面と結果ビューの実装方式、画面レイアウトの詳細
- 指標集計の実装方式（ルールベースかAI分類か）

## 1. システム概要

| 項目 | 内容 |
| --- | --- |
| システム名 | MBTI人狼シミュレーター（AI先行テスト用） |
| 種別 | 操作画面から実行するAIエージェント同士のシミュレーター。プレイヤーは全員AIエージェントであり、人間は実行と観察のみを行う。 |
| 会話の見え方 | エージェントの発言を生成しながら逐次表示するリアルタイム表示は行わない。実行完了後にまとめて表示する。 |
| 利用者 | チーム3人。実行はEngineerまたは実行担当、結果閲覧は全員。 |
| 動作単位 | 1回の実行（run）で1試合以上を進行し、結果ファイル群を出力する。 |
| 中核処理 | 心理機能を行動ルールとして持つAIエージェントが、昼議論と投票を行い、勝敗が決まる。 |
| 操作の流れ | 操作画面で条件を設定し、対戦開始ボタンで実行する。実行完了後、同じ画面で会話タイムラインと結果を確認する。 |
| 初回MVP構成 | 4人（人狼1、村人3）、昼議論3ターン、投票1回、1試合、過去ログ参照なし。 |

### 1.1 用語

| 用語 | 定義 |
| --- | --- |
| 操作画面 | 条件設定と実行開始を行い、完了後に結果を表示する画面。ローカルで起動して使う。 |
| 結果ビュー | 実行結果だけを表示する静的な画面。実行環境を持たないメンバーがブラウザで開いて使う。 |
| run | 1試合の実行単位。`run_id` で識別する。 |
| series | 複数試合をまとめた実行単位。`series_id` で識別する。 |
| 心理機能 | Ne / Ni / Se / Si / Te / Ti / Fe / Fi。エージェントの行動ルールとして扱うフィクション設定。 |
| 脳（エージェント脳） | 発言・疑い・投票を生成する推論部分。SDKやモデルを指す。 |
| history_mode | 過去ログをエージェントへ渡す範囲の指定。初回MVPは「なし」。 |
| 実行環境 | 実行したPCと推論方式。ログに記録する対象。 |

## 2. 前提条件・制約条件

### 2.1 コスト制約（最重要）

本システムは、**開発から実行までのすべてを無料の技術スタックで成立させる**ことを絶対要件とする。

| 区分 | 要件 |
| --- | --- |
| 推論（エージェント脳） | 無料枠のAPIまたはローカル実行のみを使用する。従量課金APIを前提とした構成は認めない。 |
| ライブラリ・SDK | 無料で利用できるものに限る（OSSまたは無償利用可能なもの）。有償ライセンスを必要としない。 |
| 実行環境 | メンバーが所有するMacのみ。有料のクラウド計算資源は使用しない。 |
| ホスティング・共有 | GitHubおよびGitHub Pagesの無料枠に収める。 |
| CI（使用する場合） | GitHub Actionsの無料枠に収める。無料枠を超える構成は組まない。 |
| 判定 | 課金が発生しうる構成は、採用前に却下する。判断が付かない場合は使用しない。 |

具体的にどのSDK・モデル・ランタイムを選ぶかは設計書で決定する。本書では「無料であること」を要件として固定する。

### 2.2 その他の前提

| 区分 | 前提 |
| --- | --- |
| 実行方式 | 操作画面からの起動と、コマンドからの起動の両方に対応する。実行開始後は自動進行し、途中で人の入力を必要としない。 |
| 会話の表示 | 実行完了後にまとめて表示する。1発言ずつ流すライブ表示は行わない。 |
| 実行PC | Apple Silicon Mac（M2 MacBook Air / MacBook Pro M3 18GB / Mac mini M4 16GB / MacBook M4 16GB）。 |
| 長時間・多試合実行 | Mac mini M4での夜間長時間実行を想定に含める。100回以上の実行や夜間実行は、画面を開いたままにせずコマンドから起動できるようにする。 |
| 目的 | MBTIや心理機能の正しさの証明ではなく、行動ルールの差がログに現れるかの観察。 |
| 正本 | 仕様の正本はConfluence。変更は文書に反映してから実装する。 |

## 3. 機能要件

### 3.1 ゲーム進行

| ID | 要件 | 優先度 | 検証方法 |
| --- | --- | --- | --- |
| F-01 | 指定した人数のプレイヤーを生成し、各プレイヤーに心理機能を1つ割り当てる。 | Must | 出力の `players` に人数分の `function` が記録されている。 |
| F-02 | 指定した構成で役職を割り当てる（初回MVPは人狼1、村人3）。 | Must | 出力の `players` に `role` が記録されている。 |
| F-03 | 昼議論を指定ターン数だけ進行する（初回MVPは3ターン）。各ターンで生存プレイヤーが発言する。 | Must | `timeline.md` にターンごとの発言が並ぶ。 |
| F-04 | 議論後に投票を1回行い、最多得票者を処刑する。 | Must | 出力の `votes` と処刑結果が記録されている。 |
| F-05 | 勝敗を判定する。人狼を処刑できれば村人陣営の勝ち、できなければ人狼陣営の勝ちとする。 | Must | 出力の `result` に勝敗が記録されている。 |
| F-06 | 同数得票時の決着方法を定め、常に1試合が終了する状態にする。 | Must | 同数ケースでも試合が終了し、決着方法がログから判別できる。 |
| F-07 | 1試合を人の介入なしで開始から終了まで完走する。 | Must | 1回の実行操作で結果ファイルが揃う。 |
| F-08 | 人数と役職構成を設定で拡張できる（8人、16人を想定）。 | Want | 設定変更のみで8人実行ができる。 |

### 3.2 エージェント（脳）

| ID | 要件 | 優先度 | 検証方法 |
| --- | --- | --- | --- |
| F-10 | 各エージェントは、割り当てられた心理機能に対応する行動ルールに沿って発言する。 | Must | 発言内容が心理機能ごとに異なる傾向を持つことをログで確認できる。 |
| F-11 | 役職による情報の非対称性を守る。人狼は自分が人狼であることを知り、村人は他者の役職を知らない。 | Must | 村人エージェントへの入力に他者の役職が含まれない。 |
| F-12 | 各エージェントは議論ターンで発言テキストを生成する。 | Must | `speech_text` が記録されている。 |
| F-13 | 各エージェントは投票先と投票理由を出力する。 | Must | `votes` に `target` と `reason` が記録されている。 |
| F-14 | エージェントに与えるプロンプトはバージョンを持ち、実行時に記録する。 | Must | `agent_prompt_version` が記録されている。 |
| F-15 | エージェントの脳は差し替え可能な形で扱う。推論手段を変更してもゲーム進行部分を作り直さずに済む状態にする。 | Must | 推論手段を切り替えて同じ実行ができる。 |
| F-16 | 使用した推論手段（モデル名または実行方式）を実行ごとに記録する。 | Must | 出力に推論手段の識別情報が含まれる。 |
| F-17 | 脳の応答が想定形式から外れた場合も、試合を中断させず処理を継続する。 | Must | 異常応答を含む実行でも試合が完走し、事象がログに残る。 |
| F-18 | エージェントへ過去試合の情報を渡すモードを持つ（範囲は設定で切替）。 | Want | `history_mode` を変えて挙動差を比較できる。 |

> F-15 と F-16 は、2.1のコスト制約下で無料枠の上限に達した場合に別の無料手段へ切り替えて検証を続けられるようにするための要件である。

### 3.3 設定・再現性

| ID | 要件 | 優先度 | 検証方法 |
| --- | --- | --- | --- |
| F-20 | 実験条件を設定として外部から指定できる。対象は参加人数、ターン数、試合回数、役職割当方法、seed、history_mode。指定経路は画面と設定ファイル・起動時引数の両方とする。 | Must | コードを書き換えずに条件を変更できる。 |
| F-21 | ランダム要素にseedを与え、使用したseedを記録する。 | Must | 出力の `config` に `seed` が記録されている。 |
| F-22 | 同一の設定とseedで実行した場合、心理機能の割当、役職の割当、組み合わせが再現される。 | Must | 2回実行して割当結果が一致する。 |
| F-23 | 試合回数を指定して複数試合を連続実行できる。画面を開いたままにせず実行する経路も用意する。 | Want | 10回実行が1コマンドで完了する。 |
| F-24 | 記憶リセット単位を設定できる（初回MVPは1試合ごと）。 | Want | 設定で履歴保持範囲を変更できる。 |

### 3.4 記録・出力

| ID | 要件 | 優先度 | 検証方法 |
| --- | --- | --- | --- |
| F-30 | 1試合分の全データを機械可読なログとして出力する（`run_log.json`）。 | Must | ファイルが生成され、4章のデータ要件を満たす。 |
| F-31 | 結果カードとして読める要約を出力する（`summary.md`）。 | Must | 勝敗、人狼だった機能、吊られた人、最多疑われ、最多発言が読める。 |
| F-32 | 議論の流れを追える発言ログを出力する（`timeline.md`）。 | Must | ターンと発言者が並んで読める。 |
| F-33 | 集計指標を表形式で出力する（`metrics.csv`）。 | Must | ファイルが生成され、4.3の項目を満たす。 |
| F-34 | 結果を1画面で確認できる静的な結果ビューを出力する。結果カード、メトリクス表、タイムライン、観察メモ、実行条件を含む。 | Must | ブラウザで開いて全項目が見える。 |
| F-35 | 実行の時間情報を記録する。開始時刻、終了時刻、所要時間、AI待機時間を対象とする。 | Must | 出力の `timing` に記録されている。 |
| F-36 | 実行環境（実行したPCの識別名）を記録する。 | Must | 出力の `timing` に `machine_name` が記録されている。 |
| F-37 | 実行が途中で失敗した場合も、その時点までの記録と失敗事象を残す。 | Must | 中断実行後に部分ログと失敗情報が残る。 |
| F-38 | 複数試合の結果をまとめた集計を出力する（`series_summary.md`）。 | Want | 10回実行の傾向を1ファイルで読める。 |
| F-39 | 過去ログ参照モードで、エージェントへ渡した過去情報を保存する（`history_input.json`）。 | Want | 参照した過去runが特定できる。 |

### 3.5 操作画面

操作画面は、条件設定から結果確認までを1つの画面で完結させる。会話は実行完了後にまとめて表示し、1発言ずつ流すライブ表示は行わない。

| ID | 要件 | 優先度 | 検証方法 |
| --- | --- | --- | --- |
| F-50 | 画面上で実験条件を設定できる。対象は参加人数、ターン数、試合回数、役職割当方法、seed、history_mode。 | Must | 画面の入力だけで条件を変えて実行できる。 |
| F-51 | 画面の対戦開始ボタンで実行を開始できる。ターミナル操作を必要としない。 | Must | ボタン操作のみで1ゲームが実行される。 |
| F-52 | 実行中であること、完了したこと、失敗したことが画面上で判別できる。 | Must | 各状態が画面に表示される。 |
| F-53 | 実行完了後、同じ画面で会話タイムラインと結果を表示する。 | Must | 実行後に画面遷移なしで会話と結果が読める。 |
| F-54 | 実行に使った条件を結果と一緒に画面上で確認できる。 | Must | seed、人数、ターン数、history_mode、実行環境が表示される。 |
| F-55 | 失敗時は、原因が分かる情報とその時点までの会話を画面上で確認できる。 | Must | 失敗した実行でも部分的な内容が読める。 |
| F-56 | 過去の実行結果を一覧から選んで表示できる。 | Want | 過去runを選択して結果を切り替えられる。 |
| F-57 | 画面の起動手順が単一のコマンドで完結する。 | Must | 手順書のコマンド1つで画面が開く。 |

### 3.6 共有

| ID | 要件 | 優先度 | 検証方法 |
| --- | --- | --- | --- |
| F-40 | 出力物をリポジトリにcommitできる形式・配置で保存する。 | Must | `runs/` 配下に出力が残り、commitできる。 |
| F-41 | 結果ビューは、実行環境を持たないメンバーがブラウザだけで閲覧できる。操作画面の起動を前提にしない。 | Must | ファイルを開くだけで表示され、追加インストールを要さない。 |
| F-42 | 結果画面をGitHub Pagesで公開し、URLで共有できる。 | Want | 全員がURLから閲覧できる。 |

> F-41 は、操作画面がローカル起動を必要とするのに対し、Biz・Designerが実行環境なしで結果を読める経路を維持するための要件である。操作画面と結果ビューは別経路として両方を用意する。

## 4. データ要件

出力の正本は `run_log.json` とし、他の出力はここから導出できる状態にする。schemaの詳細は設計書で定める。

### 4.1 実行単位の必須項目

| 区分 | 必須項目 |
| --- | --- |
| 実行識別 | `run_id`、`series_id`、`run_index` |
| 実験条件 | `player_count`、`turn_count`、`game_count`、`role_assignment_mode`、`seed`、`history_mode`、`history_scope` |
| プレイヤー | `player_id`、`function`、`role`、`agent_prompt_version` |
| 議論 | `turn`、`player_id`、`speech_text`、`referenced_history_ids` |
| 投票 | `voter`、`target`、`reason` |
| 結果 | 勝敗、処刑対象 |
| 時間・環境 | `started_at`、`ended_at`、`elapsed_seconds`、`ai_wait_seconds`、`machine_name` |
| 推論手段 | 使用したモデル名または実行方式の識別情報 |

### 4.2 確実に取得する指標

発言回数、平均発言文字数、投票先、吊られた人、勝敗、実行時間、AI待機時間、実行環境、seed、history_mode。

### 4.3 metrics.csv の必須列

`run_id`、`series_id`、`player_id`、`function`、`role`、`speech_count`、`avg_chars`、`final_vote`、`win`、`elapsed_seconds`。

### 4.4 できれば取得する指標

疑い回数、疑われ回数、質問回数、反論回数、同調回数、仮説数、過去ログを参照した発言数、役職変化による発言量差。これらの算出方法は設計書で決める。

## 5. 非機能要件

| ID | 区分 | 要件 | 検証方法 |
| --- | --- | --- | --- |
| NF-01 | コスト | 実行に課金を必要としない。有料の認証情報を設定しない状態で1ゲームを完走できる。 | 無料枠またはローカル実行のみで完走することを確認する。 |
| NF-02 | コスト | 使用する全ての依存が無料で入手・利用できる。 | 依存一覧と各ライセンス・料金区分を設計書に記載して確認する。 |
| NF-03 | 可搬性 | Apple Silicon Mac上で動作する。特定メンバーのPCだけで動く構成にしない。 | 2台以上のMacで実行できることを確認する。 |
| NF-04 | 導入容易性 | 実行手順が文書化され、手順に従えば環境構築から操作画面の起動まで到達できる。 | 手順書のみで画面を開いて実行できることを確認する。 |
| NF-05 | 再現性 | 設定とseedが同じなら、割当と組み合わせが再現される。脳の出力揺れは許容し、揺れる旨を記録する。 | F-22の確認結果を用いる。 |
| NF-06 | 性能可視化 | 実行時間とAI待機時間を計測して記録する。当面の目安は1試合10分以内（2026-08-15実測: 約2分50秒、ほぼ全てAI待機）。 | 記録された時間を実行後レビューで確認する。 |
| NF-07 | 耐障害性 | 無料枠の上限到達、レート制限、通信失敗が起きても、原因が判別できる形で終了し、部分結果を残す。 | 失敗ケースの記録内容を確認する。 |
| NF-08 | 継続性 | 無料枠を使い切った場合に、別の無料手段へ切り替えて検証を継続できる。 | F-15の切替確認結果を用いる。 |
| NF-09 | 拡張性 | 8人、16人、複数試合、過去ログ参照の追加が、ゲーム進行部分の作り直しなしに行える。 | 設計書のレビューで確認する。 |
| NF-10 | データ量 | 試合回数を増やしても出力がリポジトリ運用を破綻させない。 | 100回実行時の出力容量を確認する。 |
| NF-11 | 秘密情報 | 認証情報を出力物およびリポジトリに含めない。 | 出力に認証情報が含まれないことを確認する。 |
| NF-12 | 倫理 | 出力物に、実在人物の診断・評価ではないことを明示する。 | 出力またはREADMEに記載があることを確認する。 |
| NF-13 | 可読性 | 出力は、実装者以外のメンバーが説明なしで結果を読める粒度にする。 | Biz/Designerが結果を読めることを確認する。 |
| NF-14 | 操作性 | 操作画面は、設定から結果確認までを画面遷移なしまたは最小の遷移で行える。実行中に画面が固まったように見えない。 | 実行中の状態表示を確認する。 |

> NF-06 の当面の目安（1試合10分以内）は、2026-08-15 の Ollama / `gemma3:4b` 実測（約2分50秒）を見て定めた。詳細は[無料構成の確認記録](./free-stack-check.md)の6節。

## 9. リスクと対応方針

| リスク | 影響 | 対応方針 |
| --- | --- | --- |
| 無料枠の上限に達して実行が止まる | 検証が完了しない | 脳を差し替え可能にする（F-15）。ローカル実行を代替手段として確保する。 |
| ローカル推論の品質が低く議論が成立しない | 観察価値が下がる | 初回MVPは1試合で成立を確認し、品質が不足する場合は推論手段を変更して再実行する。 |
| 脳の応答形式が安定しない | 集計できない | 想定外応答でも継続する（F-17）。投票先など集計に必要な項目は形式を検証する。 |
| AI待機時間が長く実験が回らない | 規模を広げられない | 待機時間を記録し（F-35）、実測後に規模と閾値を判断する。 |
| M2 MacBook Airで負荷が高い | 実行担当が限定される | 実行環境を記録して比較し（F-36）、長時間実行はMac miniに寄せる。 |
| 出力が増えてリポジトリが重くなる | 運用が破綻する | 出力容量を確認し（NF-10）、保存方針を設計書で定める。 |
| 操作画面の実装に時間を取られ、検証本体が進まない | MVPが遅れる | 画面は結果確認に必要な範囲に絞る。見た目の完成度は問わない。 |
| 操作画面がローカル起動を要するため、Biz/Designerが使えない | 結果を見られない | 静的な結果ビューを別経路として維持する（F-41、NF-15）。 |
| 実行が長いと画面が応答なしに見える | 実行を中断してしまう | 実行中の状態を表示する（F-52、NF-14）。長時間実行はコマンド起動に寄せる（IF-07）。 |

## 10. スコープ外

- MBTIや心理機能の正しさを証明すること。
- 実在人物のタイプ診断、評価、ラベリング。
- エージェントの発言を生成しながら1発言ずつ流すリアルタイム表示。会話は実行完了後にまとめて表示する。
- 人間が遊べる人狼ゲーム（要求定義書のスコープ外を引き継ぐ）。プレイヤーは全員AIエージェントとする。
- 初回から16タイプの強さを断定すること。
- 占い師、騎士、霊媒師などの複雑役職。
- 従量課金APIを前提とした構成、および有料サービスの利用。
- 本番テーマとしてMBTI人狼を採用する前提で進めること。
